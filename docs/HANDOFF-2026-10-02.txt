1. Executive summary

HangoverBot is a deliberately narrow fantasy-football utility designed to prevent users from losing a matchup because they missed an injury, slept through inactives, forgot to set a lineup, or were otherwise unavailable when a time-sensitive roster problem happened.
The product should feel more like roster insurance than a fantasy research dashboard. Normal software watches league and football state continuously. Deterministic rules solve obvious cases. AI is called only when the situation actually requires judgment. A separate permission engine decides what may be executed automatically.
Product sentence
Connect a fantasy league, tell HangoverBot how much authority it has, and let it protect the roster when real life gets in the way.

Working positioning
AI-enabled fantasy lineup protection
Fantasy help for real life.
QUESTIONABLE — Injury Status. Life Decisions.
Product principles
Narrow beats sprawling: do not become a generic fantasy analytics suite in V1.
Rules first, AI second: deterministic software handles eligibility, locks, IR rules, clear bench swaps, and permissions.
AI is event-driven: no constant model polling and no open-ended “anything interesting?” loops.
Every write is revalidated and auditable before execution.
Trust is a UI requirement: users receive clear receipts for every automated action.
Provider differences are normalized behind capabilities rather than leaking throughout the product.

4. Authority levels

Level
Definition
1 — Alerts
Watch and notify only. Never modifies the roster.
2 — Ask Me
Identify the problem, propose a move, and require user approval.
3 — Bench Protection
Automatically repair affected lineup slots using players already on the roster. No free-agent add, waiver claim, or FAAB transaction.
4 — AI Rescue (working name)
Use AI when judgment is required; may use IR, choose bench replacements, evaluate injury-created opportunity, and add/drop immediately available free agents when the user explicitly enables those permissions. Waiver/FAAB claims remain recommendation-only in V1.
Naming note
“Full AI Optimization” sounds like an autonomous fantasy general manager. “AI Rescue” better matches the product: powerful intervention in response to a defined injury, lineup, or game-time event. Final consumer label remains open.

5. V1 scope boundary

RosterBots is intentionally reactive. It protects a user from time-sensitive roster failure; it does not independently run the team all season.

AI never wakes itself up. Normal code monitors structured state and emits events. The rules engine first determines whether the event is relevant, whether a deterministic action exists, and whether any actual judgment remains.

Initial trigger classes
Trigger
Meaning
Immediate status event
Rostered player changes state: active/questionable/doubtful/out/IR; official inactive; suspension; confirmed season-ending injury.
Scheduled game-time event
Checks relative to the actual player kickoff time. The check calls the rules engine, not automatically the model.
Opportunity event
An injury or role change materially changes the value of another player, especially where that player is available in a connected league.
User event
User explicitly taps Optimize Now / Evaluate Now.
Suggested kickoff scheduler
Potential checks: T-180, T-90, T-30, and T-10 minutes. These are rules-engine wakeups. If a starter is healthy and lineup state is valid, the result is zero AI calls.
Core cost rule
Never poll a model with “anything interesting?” Poll structured data. Only state transitions and scheduled roster checks can create AI work.

9. Bench replacement logic without AI

A normal inactive-to-bench swap should usually be a deterministic calculation. The rules engine should not spend AI tokens to answer a question already encoded in eligibility, locks, projections, and user ordering.
Filter to legal slot eligibility.
Exclude players whose games are locked or started.
Apply a user’s explicit replacement order if configured.
Apply strategy preference if enough data exists.
Otherwise use the highest projected eligible player.
Possible strategy modes
Mode
Definition
Projected
Highest conventional projection.
My Order
User-specified ranked choices; deterministic.
Upside
Requires ceiling/distribution or equivalent volatility data.
Safe
Requires floor/distribution or equivalent reliability data.
Do not fake “upside” or “safe” from a single mean projection. The football-data decision must provide the required inputs before those options ship.
10. Free agents, waivers, and FAAB

RosterBots must model player acquisition state explicitly. A player being visible in the free-agent pool does not mean the same transaction path is available in every league.
FREE_AGENT_NOW
ON_WAIVERS
LOCKED
UNAVAILABLE

Immediate free agent
If AI Rescue identifies a desirable player who is immediately addable, and the user enabled automatic FA adds, RosterBots may validate and execute the add/drop flow.
Waiver / FAAB player
V1 stops before claim submission. It may recommend the add, the drop, a suggested FAAB range, or waiver priority strategy, then notify the user. The user submits the claim.
V1 boundary
Immediate free-agent transactions can be automatic. Waiver and FAAB claims are recommendation-only.

11. AI Injury + Waiver Watch

AI is not only a Sunday feature. A major injury on Tuesday can create a waiver opportunity that disappears by Wednesday. Injury Watch should trigger when roster-relevant news materially changes player value.
INJURY EVENT
     |
     v
UNDERSTAND SEVERITY / ROLE CHANGE
     |
     v
IDENTIFY BENEFICIARIES
     |
     v
CHECK LEAGUE AVAILABILITY
     |
     v
COMPARE TO USER'S ROSTER FIT
     |
     v
RECOMMEND OR EXECUTE WITHIN PERMISSIONS

The key question is not “who is the injured player’s backup?” It is “who became more valuable because this happened, and is that player a better use of this roster spot than the alternatives?” The correct answer may be a direct backup, a committee member, or an unrelated available player with superior opportunity.

14. Fantasy-provider connector architecture

The user wants broad host coverage. Do not build provider assumptions into core business logic. Each connector declares capabilities, and the UI exposes only the authority levels/actions that connector supports.

23. Pricing and monetization — intentionally unresolved

25. Anthropic model attribution and product branding

Anthropic attribution is optional for an API-powered app. The app does not need a “Powered by Claude” badge to use the API. If the product chooses to credit the underlying model provider, keep HangoverBot/TurboLabs clearly primary, be precise about what is powered by Claude, and avoid implying that Anthropic created or endorses the app.
Recommended implementation
No Anthropic or Claude branding on the main HangoverBot home screen. If desired, place a small line in Settings → About such as “AI features powered by Claude.” This gives transparent credit without making the model provider part of the consumer brand.

Do not put Anthropic, Claude, or a model name into the app/product/company name. If a specific model is mentioned in technical documentation, keep it accurate and updateable because routing may change.

28. V1 definition of done

Install on iOS or Android.
Connect at least one supported fantasy provider and select a league/team.
Choose an authority level and configure simple protection rules.
Receive meaningful injury/game-time alerts.
Automatically make a legal bench replacement when authorized.
Call AI only for an actually ambiguous/meaningful roster decision.
Allow an immediate free-agent add in AI Rescue when authorized.
Recommend waiver/FAAB action without autonomously submitting the claim.
Show a clear activity receipt for every action.
Review/manage the same configuration from the web.
Purchase and restore the relevant entitlement.
Survive app/server restarts without losing protection state.
Log enough data to measure reliability, AI usage, and per-user cost.
Scope guard

A. Brand reference assets

The following supplied TurboLabs and TurboTips assets are embedded for visual reference. They are references for family resemblance, not a requirement to reproduce every UI detail literally.
TurboLabs primary mark

Reference cues: white forward-leaning TURBO wordmark, turbine/impeller device, vivid purple LABS label, and orange speed/energy accent. HangoverBot should feel like it belongs under the same parent brand without simply swapping the word “TIPS” for “BOT.”
TurboTips UI system reference

Reference cues: midnight/navy shell; bright purple action state; orange Turbo energy accent; white/light content cards; clear hierarchy; rounded cards and controls; mobile-first simplicity paired with a more information-dense management web surface.
HangoverBot adaptation
Keep the dark/navy foundation and purple/orange identity.
Use fewer cards and metrics than TurboTips; HangoverBot should feel lighter and more consumer-oriented.
Primary state should be reassuring: YOU’RE COVERED.
Reserve orange for energy, campaign language, warnings, and decisive actions rather than flooding every screen.
Use purple for primary interactive states and AI-enabled/protection accents.
Avoid sports-league/team marks in generic product mockups; use neutral player/team presentation until licensed data/asset strategy is finalized.
